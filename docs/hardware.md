# The board — Williams/Midway Y-Unit, as Smash T.V. uses it

Written from MAME **0.288** (`ref/mame/`, fetched verbatim from tag `mame0288`)
and from the machine itself, running under MAME against the user's romset.
Every number below is either a line of MAME source, cited, or a measurement
taken from the running game, marked *(measured)* with what was measured and
over what window. Where MAME and the documented hardware disagree, section 10
says so and says which one the gateware follows.

Files this was written from, all under `ref/mame/`:

| file | what it gives |
|---|---|
| `mame/midway/midyunit.cpp` | memory map, inputs, DIPs, clocks, machine config, ROM set |
| `mame/midway/midyunit_v.cpp` | the DMA blitter, VRAM semantics, palette, autoerase, scanout |
| `mame/midway/midyunit_m.cpp` | CMOS, protection, sound mailbox, per-game init incl. `init_smashtv` |
| `mame/midway/midyunit.h` | the state classes and what is shared with the other Y/Z-unit games |
| `mame/shared/williamssound.cpp/.h` | the Williams CVSD sound board |
| `devices/cpu/tms34010/*` | the main CPU: registers, I/O registers, video timing, interrupts |
| `devices/machine/6821pia.*` | the PIA on the sound board |
| `devices/sound/hc55516.*`, `ymopm.*` | the CVSD decoder and the YM2151 |
| `devices/cpu/m6809/*` | the sound CPU |

The driver entry is
`GAME( 1990, smashtv, 0, yunit_cvsd_6bit_slow, smashtv, midyunit_cvsd_state, init_smashtv, ROT0, "Williams", "Smash T.V. (rev 8.00)" )`
(`midyunit.cpp:3864`). Everything specific to this game follows from that one
line: **6 bits per pixel**, **CVSD sound board**, **"slow" master clock**, and
**no screen rotation**.

## 1. Parts and clocks

| part | type | clock | notes |
|---|---|---|---|
| main CPU | TMS34010 graphics processor | 40 MHz in, **÷8 → 5.00 M machine cycles/s** | `SLOW_MASTER_CLOCK` (`midyunit.cpp:1238`); the ÷8 is `tms34010.h:970` |
| video timing | generated by the TMS34010 itself | dot clock 8 MHz = 2 pixels per 4 MHz pixel clock | `set_pixel_clock(24 MHz/6)`, `set_pixels_per_clock(2)` (`midyunit.cpp:1286,1291-2`) |
| blitter | Williams custom DMA chip (L1A3787 / 5410-12239) | 1 pixel per 41 ns | the rate is MAME's `attotime::from_nsec(41 * width * height)` (`midyunit_v.cpp`, end of `dma_w`) |
| sound CPU | MC6809E | 8 MHz ÷ 4 = **2.000 MHz E** | `CVSD_MASTER_CLOCK/4` (`williamssound.cpp:188`) |
| FM | YM2151 (+ YM3012 DAC) | 3.579545 MHz | `CVSD_FM_CLOCK` (`williamssound.cpp:198`) |
| speech/effects | HC-55516 CVSD | **clocked by the 6809, one bit per pair of writes** | `williamssound.cpp:149-163` — see §6 |
| PCM | MC1408 8-bit DAC off PIA port A | written by the 6809 | `williamssound.cpp:190` |
| mailbox | 6821 PIA | — | `williamssound.cpp:191-196` |
| NVRAM | 32 KB CMOS, battery backed | — | `midyunit_m.cpp`, `machine_start` |
| protection | Intel P5C090 PLD on the board | — | **Smash T.V. never uses it**: `init_smashtv` sets `m_prot_data = nullptr` (`midyunit_m.cpp`) |

### Raster

The TMS34010 generates the raster from its own I/O registers. *(Measured:
read back from `0xC0000000+n*16` at frames 2, 60, 200 and 400 of a headless
run; identical at every sample.)*

| register | value | meaning |
|---|---|---|
| HESYNC | 0x0015 | horizontal sync end, 21 |
| HEBLNK | 0x002D | horizontal blank end, 45 → first visible dot 45×2 = **90** |
| HSBLNK | 0x00FA | horizontal blank start, 250 → last visible dot 250×2−1 = **499** |
| HTOTAL | 0x00FC | 252 → line is (252+1)×2 = **506 dots** |
| VESYNC | 0x0003 | vertical sync end, line 3 |
| VEBLNK | 0x0014 | vertical blank end → first visible line **20** |
| VSBLNK | 0x0114 | vertical blank start → last visible line **275** |
| VTOTAL | 0x0120 | 288 → **289 lines** |
| DPYCTL | 0xF010 | ENV=1 (video on), NIL=1 (not interlaced), master=1, SRT=0, **ORG=0**, DUDATE=0x10 |
| DPYSTRT | 0xFFFC | display start address |
| DPYTAP | 0x0000 | no column offset |
| DPYINT | 0x009A / 0x011A | display interrupt line — the game alternates 154 and 282 *(measured)* |
| PSIZE | 0x0008 | **8 bits per pixel** in the CPU's address space |
| PMASK | 0x0000 | no plane masking |
| CONVSP / CONVDP | 0x0013 | `1 << (~0x13 & 0x1f)` = **4096-bit pitch** = one 512-pixel row |
| CONTROL | 0x0020 | transparency on for CPU pixel writes; window checking off; raster op 0 |
| INTENB | 0x0404 | DI and INT2 enabled *(measured, after boot)* |

- **Visible picture: 410 × 256 pixels, no rotation.** Confirmed by MAME's own
  snapshot being 410×256.
- **Refresh: 4,000,000 / ((252+1) × (288+1)) = 54.7069 Hz.** The line rate is
  8 MHz / 506 = 15.810 kHz, the line 63.25 µs, the frame 18.279 ms.
- MAME hard-codes the same numbers in `screen.set_raw(8 MHz, 506, 90, 500,
  289, 20, 276)` (`midyunit.cpp:1305`) and says in a comment that Smash T.V.
  has the largest visible area of the Y-unit games, which is why it is the
  one the shared config uses.

### What paces the audio

**METHODOLOGY §5.3 applies here, hard.** Three different things pace three
parts of the sound:

- The **YM2151 is a real chip on its own 3.579545 MHz crystal**: its tempo
  does not depend on the 6809 at all.
- The **HC-55516 has no clock of its own**. Its bit clock is the 6809 writing
  `0x6000` (clock low + data bit) and `0x6800` (clock high), so **the CVSD
  sample rate is the 6809's execution rate**. Every cycle the sound CPU loses
  becomes pitch and duration error in speech and effects, directly. The 6809
  must run at exactly 2.000 MHz with no wait states — which is why its ROM
  belongs in a memory that never stalls (docs/core-design.md).
- The **MC1408 DAC** is likewise written by the 6809 in a timed loop.

## 2. Memory map — main CPU (TMS34010)

TMS34010 addresses are **bit addresses**: a 16-bit word lives at a 16-bit
aligned bit address, and a byte at an 8-bit aligned one. All ranges from
`midyunit.cpp:184-208` (`main_map` plus `cvsd_main_map`).

| range (bit addresses) | size | what | R/W | notes |
|---|---|---|---|---|
| `0x00000000-0x001FFFFF` | 2 Mbit | **VRAM window** | R/W | 512×512 pixels of 8 bits; see §7 |
| `0x01000000-0x010FFFFF` | 1 Mbit = 128 KB | main RAM | R/W | four 41464 DRAMs on the board |
| `0x01400000-0x0140FFFF` | 4096 words | **CMOS window** | R/W | one of four pages; page from `control_w` bits 7-6 |
| `0x01800000-0x0181FFFF` | 8192 words | palette RAM | W (RAM readback) | only 4096 used at 6 bpp; see §7 |
| `0x01A00000-0x01A0009F` *mirror `+0x00080000`* | 10 words | **DMA blitter registers** | R/W | the game uses the **mirror at `0x01A80000`** *(measured: every one of 1,675,350 register writes in a 45-second run)* |
| `0x01C00000-0x01C0005F` | 6 words | inputs IN0,IN1,IN2,DSW,UNK0,UNK1 | R | §3 |
| `0x01C00060-0x01C0007F` | 2 words | protection read / CMOS-enable write | R/W | read returns 0 on this game |
| `0x01E00000-0x01E0001F` | 1 word | **sound mailbox** | W | §5 |
| `0x01F00000-0x01F0001F` | 1 word | **system control** | W | §7, "control register" |
| `0x02000000-0x05FFFFFF` | 64 Mbit | graphics ROM window | R | 8 M pixels, one byte each, 2 per word |
| `0xC0000000-0xC00001FF` | 32 words | TMS34010 internal I/O registers | R/W | inside the CPU |
| `0xFF800000-0xFFFFFFFF` | 8 Mbit = 1 MB | program ROM | R | only the top 256 KB is populated |

The program ROM region is 1 MB of address space with the two 128 KB EPROMs
loaded at **offset 0xC0000 of the region**, i.e. at bit address
`0xFF800000 + 0xC0000*8 = 0xFFE00000`, and the reset vector at `0xFFFFFFE0`
is inside that. Addresses below `0xFFE00000` in the region read as zero in
MAME.

*(Measured, 90-second run through boot, attract and a played game:
4,489,404 CPU writes and 6,851,944 CPU reads to the VRAM window — of which
essentially all are the power-up RAM test, spread evenly over all 512 rows;
2,359,913 reads of the graphics ROM window, 479 per frame. Over the shorter
45-second run: 27,400 palette writes and 171 CMOS writes.)*

## 3. Inputs and DIP switches

All **active low**. From `INPUT_PORTS_START(smashtv)` (`midyunit.cpp:546`).
Offsets are the word index into `0x01C00000`.

### IN0 (offset 0) — the two joysticks per player

| bit | P1 | bit | P2 |
|---|---|---|---|
| 0 | move up | 8 | move up |
| 1 | move down | 9 | move down |
| 2 | move left | 10 | move left |
| 3 | move right | 11 | move right |
| 4 | fire up | 12 | fire up |
| 5 | fire down | 13 | fire down |
| 6 | fire left | 14 | fire left |
| 7 | fire right | 15 | fire right |

Smash T.V. is a **twin-stick** game: the left stick moves and the right stick
fires, both 8-way. This is the whole of the control design problem on a
Pocket, and `docs/core-design.md` says what was done about it.

### IN1 (offset 1) — coins and cabinet

| bit | function |
|---|---|
| 0 | coin 1 |
| 1 | coin 2 |
| 2 | start 1 |
| 3 | tilt (slam switch) |
| 4 | service mode (not a toggle) |
| 5 | start 2 |
| 6 | service credit |
| 7 | bill validator |
| 8 | video freeze (MAME: unused) |
| 9 | coin 3 |
| 10-15 | unused |

### IN2, UNK0, UNK1 (offsets 2, 4, 5)

All bits unused on this game and read all-ones. *(Measured: the program reads
offsets 0, 1 and 3 only — 6,325, 6,325 and 4,510 times in a 45-second run —
and never reads 2, 4 or 5.)*

### DSW (offset 3) — two 8-way switch banks

| bits | switch | function |
|---|---|---|
| 0-5 | DS1:8-3 | **coinage**, 27 country/price settings, 0x3F = "USA 1" = 1 coin 1 credit |
| 6 | DS1:2 | unknown |
| 7 | DS1:1 | unknown |
| 8-13 | DS2:8-3 | unknown |
| 14 | DS2:2 | "rotary joystick enable?" — MAME doubts the code supports it |
| 15 | DS2:1 | **test switch** (works on rev 6 and rev 8 only) |

The coinage switches are read **only by "full factory restore"** in the test
menu, which copies them into CMOS; changing them at any other time does
nothing. MAME says so in a comment at `midyunit.cpp:585`. That is a fact
about what a Pocket menu entry can usefully offer — METHODOLOGY §5.5, "every
menu entry is a claim that the gateware does something."

Factory default is all switches off, i.e. **0xFFFF**.

## 4. Interrupts

The TMS34010's interrupts are internal to the CPU: a pending register
(`INTPEND`), an enable register (`INTENB`) and the `IE` bit of the status
register. Vectors are read as 32-bit values from the top of memory
(`tms34010.cpp:627-700`):

| source | pending bit | vector address | priority |
|---|---|---|---|
| NMI (host) | `HSTCTLH` bit 8 | `0xFFFFFEE0` | highest |
| HI — host interrupt | 0x0200 | `0xFFFFFEC0` | |
| **DI — display interrupt** | 0x0400 | `0xFFFFFEA0` | |
| WV — window violation | 0x0800 | `0xFFFFFE80` | |
| **INT1 — external 1** | 0x0002 | `0xFFFFFFC0` | |
| INT2 — external 2 | 0x0004 | `0xFFFFFFA0` | lowest |

Taking an interrupt pushes PC then ST, resets ST to 0x00000010, loads PC from
the vector, and costs 16 cycles.

- **DI fires when `VCOUNT == DPYINT`** and video is enabled
  (`tms34010.cpp`, `scanline_callback`). Smash T.V. alternates `DPYINT`
  between **154** (mid-picture) and **282** (inside vertical blank)
  *(measured: 1,413 writes of 0x009A and 1,412 of 0x011A over 2,462 frames)*,
  so it takes two display interrupts per frame and uses one of them as a
  mid-frame raster timer.
- **INT1 is the blitter's "done"**: `dma_callback` clears bit 15 of DMA
  register 0 and asserts CPU input line 0 (`midyunit_v.cpp`). Any write to
  DMA register 0 clears it again. The game can therefore either take INT1 or
  poll bit 15 of the command register.
- **INT2 is enabled by the game but MAME never asserts it** — nothing in the
  driver drives CPU input line 1. See §10.
- `INTPEND` is mostly read-only: only `WV` and `DI` can be cleared, and only
  by writing a 0 to that bit (`tms34010.cpp:1348`).

## 5. Main CPU to sound CPU

One 16-bit write to `0x01E00000` (`cvsd_sound_w`, `midyunit_m.cpp`):

| bits | meaning |
|---|---|
| 7-0 | the command byte → PIA port B inputs |
| 8 | **/RESET for the whole sound board** — 0 holds the 6809 in reset |
| 9 | strobe → PIA **CB1** |
| 15-10 | ignored |

A write with only one byte enabled is ignored entirely (the handler requires
both `ACCESSING_BITS_0_7` and `ACCESSING_BITS_8_15`). CB2 is driven low and
never changes. There is no acknowledge path back to the main CPU on this
board other than the PIA's talkback latch, which the main CPU cannot read.

*(Measured: 8-bit command values seen in a 45-second run run from 0x00 to
0xFF with bit 8 of the written word always 1 except for two `0xFE00` writes
— the reset pulse at start-up.)*

## 6. Sound board — Williams CVSD (`5766-12702-00 REV. B`)

`williamssound.cpp:170-184`, memory map of the MC6809E:

| range | what |
|---|---|
| `0x0000-0x07FF` (mirror `0x1800`) | 2 KB RAM (the 6116) |
| `0x2000-0x2001` (mirror `0x1FFE`) | YM2151 |
| `0x4000-0x4003` (mirror `0x1FFC`) | 6821 PIA |
| `0x6000` (mirror `0x07FF`) | CVSD: clock **low**, and latch data bit 0 |
| `0x6800` (mirror `0x07FF`) | CVSD: clock **high** |
| `0x7800` (mirror `0x07FF`) | ROM bank select |
| `0x8000-0xFFFF` | banked ROM, 32 KB window |

### Banking

`bank_select_w` takes the low 4 bits (`williamssound.cpp:127`), and
`device_start` lays the banks out as
`0x8000 * ((bank >> 2) & 3) + 0x20000 * (bank & 3)` from region offset
`0x10000` (`williamssound.cpp:213-228`), with the comment:

```
D0/D1 -> selects: 0=U4 1=U19 2=U20 3=n/c
D2 -> A15
D3 -> A16
```

Smash T.V.'s three sound EPROMs are 64 KB each and MAME loads each one twice
(`ROM_RELOAD`), which is exactly what a 64 KB part in a 128 KB socket does:
**A16 is a don't-care**. So the bank number means: bits 1-0 choose U4 / U19 /
U20 / nothing, bit 2 chooses the low or high 32 KB half of that EPROM, bit 3
does nothing.

### The PIA

`williamssound.cpp:186-201`:

| PIA line | connected to |
|---|---|
| port A out | MC1408 DAC |
| port B out | talkback latch (nothing reads it here) |
| port B in | the command byte from the main CPU |
| CB1 in | the command strobe from the main CPU |
| CB2 in | tied low by the driver |
| CA1 in | YM2151 IRQ, **inverted** |
| CA2 out | YM2151 /RESET |
| IRQA out | 6809 **FIRQ** |
| IRQB out | 6809 **NMI** |

So: a command from the main CPU raises CB1 and reaches the 6809 as an NMI; a
YM2151 timer interrupt reaches it as a FIRQ.

### Mixing

`add_route` weights (`williamssound.cpp:199-207`): YM2151 **0.10**, MC1408
DAC **0.25**, HC-55516 **0.60**, all to one mono speaker. These are the
numbers to derive the mix from — METHODOLOGY §5.12, *derive, do not fit*.

### The sound-ROM write window

`init_smashtv` calls `init_generic(6, SOUND_CVSD_SMALL, 0x9CF6, 0x9D21)`
(`midyunit_m.cpp`). `SOUND_CVSD_SMALL` installs a write handler over 6809
addresses **0x9CF6-0x9D21** (44 bytes) that redirects writes into the sound
ROM image at bank 0, with the comment "because the entire CVSD ROM is banked,
we have to make sure that writes go to the proper location". This is a
protection workaround in MAME, not a description of a chip. §10 has it as an
open question: it has to be understood before the sound board is built,
because a real board has no RAM there.

## 7. Video

The Y-unit has no tilemaps and no sprite list. It has **one 512×512 frame
buffer**, a **blitter** that draws into it from the graphics ROM, and a
**scanout** that walks it a row per raster line. All drawing is the blitter's;
the CPU only touches the frame buffer directly for the power-up RAM test and
the occasional poke.

### 7.1 The frame buffer

512 rows × 512 columns. Each pixel is **two bytes in two planes**:

```
   pixel entry = { palette byte [15:8] , pixel byte [7:0] }
```

At 6 bits per pixel only 12 of the 16 bits reach the palette. The pen index
is (`midyunit_v.cpp`, `VIDEO_START_MEMBER(midyunit_6bit)`):

```
   pen[11:0] = { entry[11:8], entry[15:14], entry[5:0] }
             = { palette[3:0], palette[7:6], pixel[5:0] }
```

— that is, six bits of pixel and six bits of palette, in that order on the
palette RAM's address pins. `palette[5:4]` and `pixel[7:6]` go nowhere.

### 7.2 What the CPU sees through the VRAM window

`vram_r` / `vram_w` (`midyunit_v.cpp`). The **video bank select** bit (bit 5
of the control register, §7.5) chooses which plane the CPU addresses. A word
access covers **two adjacent pixels**, low byte first:

| videobank | CPU write of `d` at word offset `o` | CPU read |
|---|---|---|
| 1 | `px[2o] = {DMA_PALETTE[7:0], d[7:0]}`, `px[2o+1] = {DMA_PALETTE[15:8], d[15:8]}` | `{px[2o+1][7:0], px[2o][7:0]}` |
| 0 | `px[2o][15:8] = d[7:0]`, `px[2o+1][15:8] = d[15:8]` (pixel bytes kept) | `{px[2o+1][15:8], px[2o][15:8]}` |

With the pixel bank selected, **a CPU pixel write also loads the palette
plane from the blitter's palette register**. That is a wire on the board: the
DMA palette latch drives the palette plane's data inputs whichever side is
writing.

### 7.3 The blitter

Ten 16-bit registers at `0x01A80000` (the game's mirror), stride 16 bits,
from the table in `midyunit_v.cpp` above `dma_w`:

| reg | name | meaning |
|---|---|---|
| 0 | COMMAND | bit 15 triggers; see below |
| 1 | ROWBYTES | signed source bytes to skip per row |
| 2 | OFFSETLO | source bit address, low word |
| 3 | OFFSETHI | source bit address, high word |
| 4 | XSTART | signed destination x |
| 5 | YSTART | signed destination y |
| 6 | WIDTH | pixels across |
| 7 | HEIGHT | rows |
| 8 | PALETTE | palette byte, in the high half |
| 9 | COLOR | solid colour, low byte |

Command word:

| bit | meaning |
|---|---|
| 15 | trigger on write; cleared by the chip when the blit finishes |
| 5 | flip y — **MAME does not implement it**, see §10 |
| 4 | flip x |
| 3 | draw non-zero source pixels as COLOR |
| 2 | draw zero source pixels as COLOR |
| 1 | draw non-zero source pixels as themselves |
| 0 | draw zero source pixels as themselves |

The low four bits select one of sixteen behaviours; `dma_draw` is the
specification and the reference renderer implements it case for case. The
four that Smash T.V. uses *(measured over 167,279 blits in a 45-second
run)* are `0x2` "draw non-zero pixels" (164,629, with and without either
flip), `0x8` "colour non-zero pixels" (2,339), `0xC` "colour all pixels"
(310) and `0x3` "draw all pixels" (1). Bit 11 (`0x0800`) is set on 60,158 of
them and MAME ignores it; flip x on 45,097 and flip y on 6,360.

**Draw order**, as numbered steps, from `dma_w` then `dma_draw`:

1. Latch ROWBYTES (signed), XSTART (signed), YSTART (signed), WIDTH, HEIGHT,
   PALETTE `<< 8`, COLOR `& 0xFF`.
2. Form the source bit address from OFFSETHI:OFFSETLO.
3. If flip x: subtract `(WIDTH-1) * 8` from the source address, set
   `ROWBYTES = (ROWBYTES - WIDTH + 3) & ~3`, and move XSTART to
   `XSTART + WIDTH - 1`. Otherwise `ROWBYTES = (ROWBYTES + WIDTH + 3) & ~3`.
4. Clip in y: if YSTART < 0, lose that many rows off the top and advance the
   source by `-YSTART * ROWBYTES` **bits** (`<< 3`); clamp
   `YSTART + HEIGHT` to 512.
5. Clip in x, in whichever direction the blit runs; adjust the source by the
   clipped pixels.
6. If the source address is below `0x02000000`, add `0x02000000`; subtract
   `0x02000000` to index the graphics ROM in pixels.
7. For each row: `ty = (YSTART + y) & 0x1FF`; the destination row is
   `ty * 512`; the source for the row starts at the running offset, which
   advances by ROWBYTES per row. If the source offset is past `0x06000000`
   and the command is a copy rather than a fill, skip the row.
8. Across the row, `tx` starts at the (clipped) XSTART and steps by −1 when
   flip x is set, +1 otherwise. Each source pixel is one byte of the graphics
   ROM; what is written depends on the command's low four bits.
9. When the blit ends, clear command bit 15 and assert INT1, after
   `41 ns × WIDTH × HEIGHT`.

Note what the blitter **never** does: it never reads the destination. Every
one of the sixteen cases decides from the *source* pixel alone. That is worth
a line of its own because it means the frame buffer needs no read-modify-write
path.

### 7.4 Scanout and autoerase

Per visible raster line (`midyunit_v.cpp`, `scanline_update`), with the
address the TMS34010 hands it:

1. `rowaddr` comes from the CPU's `DPYADR`, which is loaded from `DPYSTRT` at
   the start of vertical blank and decremented by `DUDATE` once per visible
   line; because **ORG is 0**, `get_display_params` inverts it
   (`dpyadr ^= 0xFFFC`), which turns the count back into 0, 1, 2, … So
   **visible line *n* shows frame-buffer row *n***, for *n* = 0…255.
2. `coladdr` works out to 0 for every line on this game, so the visible window
   is **frame-buffer columns 0…409** at screen dots 90…499.
3. Each pixel is looked up through the 6-bit pen map of §7.1 and then the
   palette.
4. **Autoerase**: after the line is displayed, if autoerase is enabled
   (control register bit 4 low), row *n* is overwritten with a copy of row
   **510 + (n & 1)**. Two template rows, chosen by line parity. This is how
   the game clears the screen for nothing, and it is why the blitter fills
   rows 510 and 511 with the background colour at start-up *(measured: three
   `cmd=0x800C x=0 y=510 w=511 h=2 col=0x3D3D` blits in a 90-second run, and
   no other blit to any row above 255 except one to row 257)*.

*(Measured, 90-second run: the blitter wrote to rows 0-255 11,859,046 times,
to row 257 once, and to rows 510-511 six times. The CPU, by contrast, swept
every one of the 512 rows evenly — the power-up RAM test.)*

### 7.5 The system control register (`0x01F00000`)

Only the low byte exists; the high byte is open bus
(`control_w`, `midyunit_v.cpp`):

| bit | function |
|---|---|
| 7-6 | CMOS page (× 0x1000 words) |
| 5 | video bank select — 1 = CPU sees the pixel plane |
| 4 | **/autoerase enable** — 0 enables autoerase |
| 3 | N/C on Y-unit ("EXT" on later schematics) |
| 2 | /LED |
| 1 | watchdog data ("WD.DAT") |
| 0 | watchdog clock ("WD.CLK") |

*(Measured: the values written are 0xFF2C/2D/2E/2F, 0xFF3C…3F, 0xFF6C…6F,
0xFF7C…7F, 0xFFBC, 0xFFDC, 0xFFEC, 0xFFFC…FF — i.e. CMOS pages 0, 1 and 3,
video bank always 1, autoerase toggled on and off, and bits 1-0 walking
through all four combinations, which is the watchdog being kicked.)*

The watchdog is an EP800 PLD counting these pulses; nothing in MAME models
it. **It counts wall-clock time while the CPU is stopped** — METHODOLOGY
§5.5's warning about `pause_core`.

### 7.6 Palette

4096 entries of 16 bits at `0x01800000`, written as
`x RRRRR GGGGG BBBBB` and expanded with `pal5bit` (5 bits → 8 by bit
replication: `v<<3 | v>>2`). Bit 15 is unused.

## 8. ROMs

The user's romset carries the pre-0.240 short names. Every file was matched to
MAME 0.288's `ROM_START(smashtv)` **by CRC32**, not by the number in the name;
`tools/shadow_romset.sh` holds the mapping and `tools/verify_rom.py` re-checks
it every time the image is built.

### How the graphics ROMs become pixels

`init_gfxrom(6)` (`midyunit_m.cpp`) turns the `gfx` region into a linear array
of one byte per pixel. The region is 8 MB seen as **four 2 MB chunks**; at 6
bits per pixel the first three chunks each carry **two bits of every pixel**,
packed four pixels to a byte:

```
   pixel p, plane pair c (0,1,2):
       bits = ( gfx[c * 0x200000 + (p >> 2)] >> (2 * (p & 3)) ) & 3
   pixel value = bits(c=0) | bits(c=1) << 2 | bits(c=2) << 4
```

Chunk 0 is u111+u112+u113, chunk 1 is u95+u96+u97, chunk 2 is u106+u107+u108,
each 0x60000 bytes of a 0x200000 chunk; the rest reads as zero. So
**0x60000 × 4 = 1,572,864 pixels** of the 8 M the address space allows are
real, and the blitter's source addresses never exceed them in practice.

The CPU's view of the same data (`gfxrom_r`) is one byte per pixel, two
pixels to a 16-bit word, **low pixel first**.

## 9. What the program actually uses

*(All measured, 45- to 90-second headless runs covering boot, the ROM check,
attract mode, the high-score table, a coin-up and a played game.)*

**Used:**

- DMA blitter commands `0x02`, `0x03`, `0x08`, `0x0C` with and without flip x
  (`0x10`) and flip y (`0x20`), and with bit `0x0800` set or clear.
- Autoerase, switched on and off during a frame.
- CMOS pages 0, 1 and 3.
- Display interrupt at two scanlines per frame; INT1 from the blitter.
- Input ports IN0, IN1 and DSW.
- The CPU's own transparent pixel writes (CONTROL bit 5 set, PSIZE 8).

**The TMS34010 instructions it executes.** *(Measured with MAME's debugger
trace over twelve windows of twelve frames — reset, the RAM and ROM tests, the
CPU drawing text, a screen clear, title, attract, coin-up, game start and two
of play: 5,145,825 instructions.)* 86 mnemonics in 130 operand forms. In
order of frequency: MOVE (16 addressing forms, of which register-register,
`R,*R+`, `*R(n),R`, `*R,R`, `*R+,R` and `@n,R` are 97%), DSJS, the sixteen
conditional jumps, SLA, ADDC, CMP, SRL, ANDI, ZEXT, MOVI, ORI, OR, ADD,
MMTM/MMFM (always through SP bar seven MMFMs through A8), RETS, CALLA,
SUBXY/ADDXY/CMPXY, CLR, MOVX/MOVY, SLL, ADDI, DEC, INC, RETI, BTST, CALLR,
CMPI, MOVB (five forms), MPYU, NEG, MOVK, DINT/EINT, AND, PUSHST/POPST, XOR,
ADDK/SUBK, MPYS, JUMP, SUB, NOT, DSJ, SETF, ANDN, TRAP, RL, EXGPC, GETPC,
CLRC/SETC, DIVU, ABS, SEXT, CALL, LMO, EXGF, CVXYL, DIVS.

Field sizes set with SETF are only ever 16 and 32, but the power-up RAM test
loads the field size from a table in ROM with EXGF, so the general 1-to-32-bit
field machinery has to work or the game fails its own memory test.

The CPU's own graphics instructions are nearly unused: **PIXT `*R,R`** 92
times in the game proper, and then — only inside the power-up self-test at
`0xFFF4F8xx-0xFFF4FExx` — DRAV 100 times, FILL XY 6, PIXBLT B,XY 5 and
PIXT `R,*R,XY` once. LINE, the other five PIXBLT forms, FILL L, CPW and the
other PIXT forms never execute. Everything the player sees is drawn by the
board's blitter, not by the graphics processor's graphics instructions.

**Not used, and therefore not built** — each of these must be re-checked
before it is left out for good:

- Window checking / window violation interrupt (CONTROL bits 7-6 are 0).
- Plane masking (PMASK is 0, and MAME logs an error if it ever is not).
- Raster ops (CONTROL bits 14-10 are 0, so pixel writes replace).
- The host interface (HSTCTLL/HSTCTLH written twice with 0 at reset and never
  again; nothing on the board drives them).
- Shift-register transfers (DPYCTL bit 11 is 0), although the Y-unit wires the
  VRAM shift registers up and the autoerase is what uses them.
- Interlace (DPYCTL bit 14 is 1 = non-interlaced; MAME calls `fatalerror` if
  a Y-unit game ever clears it).
- Input ports IN2, UNK0 and UNK1 — never read.
- The protection PLD — `init_smashtv` explicitly disables it.

## 10. Open questions

1. **Blitter flip-y (command bit 5).** MAME reads the bit into its log and
   then ignores it: `dma_draw` always steps the destination row forwards. The
   game sets it on 6,360 of 167,279 blits *(measured)*. Either the hardware
   achieves vertical flip through a negative ROWBYTES (which MAME does
   implement, and which would make bit 5 redundant), or MAME has a latent
   inaccuracy that nothing in this game shows. **The gateware follows MAME**
   until the reference renderer disagrees with a MAME frame on a blit that
   sets it; the renderer is where this gets settled, not the RTL.
2. **Command bit 11 (`0x0800`).** Set on 36% of blits, unknown to MAME,
   ignored. Same resolution path as (1).
3. **INT2.** The game enables it (INTENB = 0x0404) and nothing in MAME ever
   asserts it. What is on that pin on a Y-unit board is not known here. If it
   is the blitter and INT1 is something else, a core that gets them the wrong
   way round would look right in simulation against MAME and wrong on
   hardware — so this needs the schematic or a `-log` of the game's vector
   table before the CPU is wired up.
4. **The 6809 write window at 0x9CF6-0x9D21.** MAME redirects writes there
   into the sound ROM image. Whether the real board has RAM at those
   addresses, or the game is writing to ROM and reading back the ROM's own
   contents, changes what the sound board must do. Resolve with Ghidra on
   `sl2.u4` before building the sound board.
5. **The watchdog.** The EP800 counts the toggling of control bits 1-0 (and
   possibly the TMS34010's /BLANK). Its period is not known. Nothing in MAME
   models it, so nothing here can be checked against MAME; the number matters
   only for how long `pause_core` may hold the CPU before the board resets
   itself.
6. **Exact blitter timing.** MAME's 41 ns per pixel is a single flat number
   with no per-row or per-blit overhead. Real silicon will have a setup cost
   per row at least. The number that matters for the core is whether the
   worst frame fits, and that has been measured against MAME's model
   (§ docs/core-design.md); a more accurate model would only be needed if the
   game turns out to be sensitive to it.
